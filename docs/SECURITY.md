# Security

Threat model outline. Each milestone fills in its rows with the controls it adds and the tests that
prove them.

## Tenant isolation

| Threat                                    | Control                                                                                                                                                                | Evidence                                     |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| User of gym A reads or edits gym B's data | Service layer scoping (`withTenant` + `tenantScope`), RLS on every tenant table, composite FKs                                                                         | `tenancy.int.test.ts` "isolation, …"         |
| Forged tenant id from the client          | Active tenant lives on the server-side session and is re-verified against membership per request                                                                       | `loadTenantAccess` returns null; tested      |
| Developer forgets a filter / new table    | RLS fails closed (NULL tenant → no rows); registry test; RLS-on-every-table test                                                                                       | `registry.test.ts`, `tenancy.int.test.ts`    |
| Platform staff browse gym business data   | `gym_platform` has no rights on schema `app`; only `platform_api` functions; support sessions are reasoned, ≤ 2 h, read-only, logged on both sides, visible to the gym | "realm separation", "support sessions" tests |
| Branch-scoped staff act on another branch | Branch-scoped permission keys; `hasPermission(..., { branchId })`                                                                                                      | "branch-scoped roles" tests                  |

## Authentication (D-03)

| Threat                                      | Control                                                                                                                                                     |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tenant session used in the platform console | Separate secrets, cookie names, session tables and DB roles; tested both ways (`auth.int.test.ts`, e2e)                                                     |
| Password guessing                           | Redis limits per IP and per account; 5 failed passwords lock the account for 15 min                                                                         |
| Stolen password (owner/admin/platform)      | Mandatory email OTP; 6 digits, 10-min TTL, HMAC at rest, single use, 5 attempts, 30 s resend cooldown, rate-limited                                         |
| OTP / invite / reset brute force            | Per-IP and per-account Redis limits on every such endpoint                                                                                                  |
| Account enumeration on password reset       | Same response whether or not the account exists                                                                                                             |
| Session theft                               | httpOnly cookies, `Secure` in production, 7-day tenant / 12-hour platform sessions; users can list and revoke sessions; password reset revokes all sessions |
| Deactivated user keeps access               | Session creation hook refuses deactivated users; every request re-checks user and membership status                                                         |
| Open redirect via `next=`                   | `safeNext()` only accepts same-site relative paths                                                                                                          |

## Secrets and personal data

- Secrets come from the environment (AWS Secrets Manager / SSM in production). Production refuses the
  development placeholder secrets and identical realm secrets.
- The logger redacts passwords, tokens, OTPs, secrets, cookies and card/health fields. Audit entries are
  redacted the same way before storage.
- Invitation tokens, trusted-device tokens and OTPs are stored only as hashes.
- Uploads (logos) go straight to a private bucket through a presigned POST that pins key, type and size;
  the server re-checks the object before saving it. Reads use short-lived presigned URLs.

## Payments and SaaS billing (M4)

| Threat                                              | Control                                                                                                                                                                                     | Evidence                                                                                                                                        |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Forged payment webhook                              | HMAC-SHA256 of the raw body with the integration's webhook secret, constant-time compare, checked **before** the body is parsed; failure → 400 and nothing stored                           | `m4.int.test.ts` "rejects a forged signature and writes nothing"; admin e2e "forged platform webhooks are refused"                              |
| Replayed / duplicated / reordered webhooks          | Stored once per provider event id (unique); one payment per provider payment id (unique); per-link row lock; state re-fetched from Razorpay on every event                                  | "same event delivered 3 times", "partial then remainder (out of order)"                                                                         |
| Gym B's endpoint used for gym A's events            | Webhook URL carries the integration id; events are matched to links of that integration only                                                                                                | "tenant B's integration can't process tenant A's events"                                                                                        |
| Redirect / callback tampering marks an invoice paid | The return page only polls our API; only verified webhooks or a direct fetch from Razorpay record payments                                                                                  | `myPaymentStatus`; e2e "member pays their balance online"                                                                                       |
| Payment keys leak from the database                 | Key and webhook secrets envelope-encrypted (`DATA_ENCRYPTION_KEY`), never returned to the browser (last 4 only), never in audit or logs                                                     | "stores secrets sealed and shows only the last 4"                                                                                               |
| Webhook payload stores card data                    | Payloads redacted before storage (card, bank, VPA, contact fields)                                                                                                                          | `redactPayload`                                                                                                                                 |
| Refund abuse                                        | `billing.refund`; amount ≤ what's left; optional second approver (not the requester) above a threshold; credit note first; audited                                                          | "refund: credit note … big refunds need a second person"                                                                                        |
| Platform billing touches gym data                   | Platform webhook endpoint and jobs use `gym_platform`, which has no rights on `app`                                                                                                         | "platform webhooks run on gym_platform, which can't touch gym tables"                                                                           |
| Gym app forges a subscription change                | Gym app checks `subscription.manage`, then calls the admin app with an HMAC (`PLATFORM_INTERNAL_SECRET`) over timestamp, path and body (5-minute window); the admin app re-reads everything | `billing-units.test.ts`, "owner billing: only subscription.manage sends a signed request"; admin e2e "unsigned internal requests … are refused" |
| Test payment provider in production                 | `PAYMENTS_FAKE_ENABLED` refused by the env check in a real production deploy; dev checkout pages 404 unless enabled                                                                         | `packages/env` `checkSecrets`                                                                                                                   |

## Member privacy and retention (M4 launch minimum)

- **Notice and consent**: members see the privacy notice (versioned, `PRIVACY_NOTICE_VERSION`) before
  using the app; acceptance is stored with the version and time and audited. A new version asks again.
- **Download my data**: JSON of profile, memberships, invoices, payments, consents, check-ins and
  bookings; each download is recorded and audited.
- **Request deletion**: creates a request for staff (owners/admins are notified). Staff with
  `members.delete` complete it after checking dues; nothing is deleted automatically.
- **What deletion does**: personal fields (name, phone, email, date of birth, gender, address,
  emergency contact, photo, tags) are wiped and the profile is marked anonymised; staff notes are
  deleted; the pass is revoked, future bookings cancelled, the member's app access to that gym removed.

Retention policy:

| Data                                                     | Kept for                                                            | Why                                                                                                                   |
| -------------------------------------------------------- | ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Invoices, credit notes, payments, refunds, SaaS invoices | 8 years from the end of the financial year (no deletion by the app) | GST record-keeping (CGST Act s.36: 72 months after the annual return due date) — _to be confirmed by the client's CA_ |
| Audit log                                                | 8 years                                                             | Supports the financial records above                                                                                  |
| Anonymised member profile                                | As long as its invoices                                             | Invoices keep their own name snapshot as issued                                                                       |
| Check-ins, bookings                                      | Life of the gym account; anonymised with the member                 | Operations and KPIs                                                                                                   |
| Webhook events (redacted)                                | Not purged yet — proposed 180 days                                  | Debugging and reconciliation                                                                                          |
| Logs (CloudWatch)                                        | 30 days on staging, 90 days proposed for production                 | Operations                                                                                                            |

Not built yet: automatic purge jobs for the "proposed" rows, health data rules (M7), and consent for
promotional messages (M6).

## CRM and public capture (M5)

| Threat                                                      | Control                                                                                                                                                                                          | Evidence                                                                          |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| A public form or API call writes into another gym or branch | The form key (or API key) alone decides the tenant and branch, found through SECURITY DEFINER lookups; body fields like `tenantId`/`branchId` are ignored (form) or refused (API, strict schema) | `m5.int.test.ts` "form → lead…", "API keys…"; e2e "public capture is tenant-safe" |
| Form spam / abuse                                           | Honeypot (stores nothing, looks successful), 10/h per IP and 300/h per form, consent tick required, captcha hook ready                                                                           | "form → lead…" test                                                               |
| Embedding the form to trick visitors (clickjacking)         | Hosted form: `X-Frame-Options: DENY`. Embed variant: plain HTML, `frame-ancestors` limited to the form's allowed sites, `default-src 'none'`                                                     | e2e header checks                                                                 |
| Leaked API key                                              | Only a SHA-256 is stored, constant-time compare, shown once, one scope, revocable at once, 600/h per key; `Idempotency-Key` prevents duplicate leads on retries                                  | "API keys…" test                                                                  |
| Staff of one branch see another's leads                     | `leads.*` keys are branch-scoped; reads return not-found outside the user's branches; RLS per tenant                                                                                             | "isolation" test                                                                  |
| Promotional messages without consent                        | The exact consent text and time are stored on each lead; marketing consent is a separate, unticked box. (Sending is M6, which must check it.)                                                    | lead fields                                                                       |
| Trial pass misuse                                           | Random code, no personal data in the QR, valid at the trial's branch on its day, once                                                                                                            | "trial → conversion…" test                                                        |
| Lost or duplicated automation triggers                      | Events written in the change's transaction (outbox); each handler runs once (`event_consumption`, append-only); failed relays are visible and retryable by the operator (metadata only)          | "events and the CRM tick", "job hardening" tests                                  |

**Deployment note (rate limits):** limits key on the first `X-Forwarded-For` value. That is the real client
only when the reverse proxy _overwrites_ the header (Caddy does by default; the staging setup uses Caddy). Behind
a load balancer that _appends_ (e.g. AWS ALB), the first value is client-controlled: configure the proxy, or
change `clientIp` to read the trusted hop, before going live that way.

## WhatsApp, campaigns and automation (M6)

| Threat                                           | Control                                                                                                                                                                                                                                                                                 | Evidence                                                                                                 |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Forged Meta webhook                              | `X-Hub-Signature-256` HMAC over the **raw body** with `META_APP_SECRET`, constant-time compare, checked before parsing; no secret configured = everything refused (401). GET handshake answers only the right verify token                                                              | `m6.int.test.ts` "rejects a forged signature"; e2e posts a wrongly signed body (401); `whatsapp.test.ts` |
| Gym X's WhatsApp events land in gym Y            | Routing only by phone number id via `app.whatsapp_route` (disconnected accounts excluded), then the stored account's WABA id must match the payload's; unknown items are dropped, never guessed. One number belongs to one gym (partial unique)                                         | "routes by phone number id; WABA X's events never touch tenant Y"; "a number belongs to one gym"         |
| Leaked WhatsApp token                            | Sealed with the data key (`SecretBox`), never returned to the browser, never logged or audited (last 4 only); errors never echo it                                                                                                                                                      | "seals the token…" test; adapter test "never exposing the token"                                         |
| Promotional message without consent / after STOP | Checked **at send time** for every message (not when a campaign is built): MARKETING needs the latest WhatsApp marketing consent GRANTED; any active suppression blocks every category; opt-out keywords suppress at once and skip queued promotions; Meta error 131050 revokes consent | "UTILITY needs service consent…", "STOP: suppression…", campaign test "STOP after scheduling still wins" |
| Spamming members                                 | Per-number daily cap on promotional messages (campaigns + automations, default 1); throttle per campaign; messaging-limit tier respected when releasing batches                                                                                                                         | "caps promotional messages…" unit + integration tests                                                    |
| Free text outside the 24-hour window             | Refused in the inbox and again by the send gate                                                                                                                                                                                                                                         | "free text only inside the 24-hour window"                                                               |
| Duplicate sends (retries, two workers)           | Unique idempotency key per send; the worker locks the row, re-checks and claims QUEUED → SENDING; SENDING is never resent; webhook items deduped and locked while processed                                                                                                             | "a transient failure is retried… exactly once", "the same send delivered twice at once…"                 |
| Runaway or double automations                    | One execution per (version, trigger) by unique index, never twice per workflow + trigger; each step recorded once (unique step run, written in the step's transaction); predefined step types only, no user code; approval steps need `automations.approve` for the branch              | "a duplicate trigger runs once…", "an approval step blocks…"                                             |
| Segment injection                                | Audiences are a Zod-validated DSL over a fixed field list compiled to Prisma filters (no SQL, no free field names)                                                                                                                                                                      | `segment-dsl.test.ts` "rejects unknown fields… injection attempts"                                       |
| Open redirect via "back" links                   | Template-send actions only redirect to same-site paths                                                                                                                                                                                                                                  | `inbox/actions.ts`                                                                                       |

Embedded Signup: the code is exchanged for a token **server-side** (the app secret never reaches the browser);
the flow stays hidden behind the platform flag plus Meta app config. The Facebook SDK loads only on that page
and only when enabled; there is no global CSP today (if one is added, it must allow `connect.facebook.net`).

## Health and fitness data (M7)

| Threat                                                  | Control                                                                                                                                                                                                                                | Evidence                                                             |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Fitness/health data stored without permission           | A separate health-data consent (versioned text, append-only history) is required before any plan, log, measurement, goal or food/water entry; withdrawing it stops new records and staff access                                        | `m7.int.test.ts` "nothing is stored before…", "withdrawing consent…" |
| Front-desk, sales or accounts staff reading health data | Not reachable through `members.view`: only the assigned trainer (`fitness.manage` + active assignment), Owner/Admin (`fitness.view_all`) or the member. Others get 403; unassigned trainers and other branches' managers get not-found | "only the assigned trainer and owner/admin…"                         |
| Member A reading member B's logs                        | Every member call is scoped to the signed-in member; another member's ids look like missing records                                                                                                                                    | "member logs today's workout…" (B can't read or write A's workout)   |
| Silent snooping                                         | Every staff view of a member's workouts, progress or nutrition writes an audit row (who, which member, via trainer/view-all). Measurement values never go into the audit log                                                           | audit assertions in the same tests                                   |
| Health data leaking through exports                     | General member CSV export contains none of it; a separate JSON export needs `fitness.export` (Owner/Admin) and is audited; the member's own data download includes their fitness data                                                  | "health data is never in the general member export…"                 |
| Data kept after deletion                                | Completing a deletion request calls `app.erase_member_health_data` in the same transaction (the app role can't delete those rows otherwise)                                                                                            | "deleting the member erases their health data"                       |
| Medical claims                                          | Fixed, non-medical copy on plan, workout, progress and diet pages; assessment notes say "no diagnoses"; no BMI or health scoring                                                                                                       | UI                                                                   |
| Gaming points / overtraining incentives                 | Visit once a day, weekly cap, weeks-based streaks; every award has a unique source key; redemption checks the balance under a per-member lock in the same transaction as the credit entry                                              | rewards / streak tests incl. concurrent redemption                   |
| Referral abuse                                          | Random codes without personal data; tenant and referrer only from the code (SECURITY DEFINER lookup); rate limits (10/h per IP, 50/h per code); existing members can't be "referred"; self-referral rejected; reward once              | "referral link → lead…"                                              |

## Reports, exports and the AI Copilot (M8)

| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A branch manager seeing other branches in reports, exports or the Copilot | Every KPI, report, export and Copilot tool resolves its scope from the AuthContext: branches narrowed to the caller's grants for the permission; asking for another branch is 403. Money needs `reports.financial` for every branch in scope.
